# 전체 소스 검토와 완료 조건

## 시작 시 대상 전체를 고정한다

대상 소스의 기본 검토 범위는 100%다. 시작 즉시 모든 소스 루트를 등록하고 전체 파일 목록·원본 바이트 SHA-256·줄 수를 CPU 작업으로 생성한다. `workspace.py init`이 `evidence/source-inventory.json`을 만들며, 목록화했다고 의미 검토까지 완료된 것은 아니다.

Git 추적 여부, 숨김 여부, vendor·생성 코드·테스트·마이그레이션·설정이라는 이유로 소스를 생략하지 않는다. 확장자 화이트리스트로 조사 대상을 제한하지 않는다. Git 내부 자료와 키트 자신의 조사 출력·도구 캐시만 기술적 제외로 기록한다. 그 밖의 파일을 에이전트가 임의로 제외해 100%를 만들지 않는다. 범위 변경은 사용자의 명시적 결정과 변경 이력을 따른다.

UTF-8 텍스트 파일 전체를 기본 소스·문맥 검토 분모에 포함한다. 파일·구간·함수·경로 단위를 나누어 검토하되 공통 정책, 호출자·피호출자, 데이터·권한·상태 연결도 추적한다. 각 단위는 `coverage.json.units[]`에 질문·의미 검토 결과·소스 참조를 기록한다. `reviewed` 참조의 줄 구간 합집합으로 전체 파일·줄 커버리지를 계산하며 겹치는 구간은 중복 가산하지 않는다. 빈 파일도 `coverage.json.empty_files[]`에 루트·경로·전체 해시·확인 이유·검토자를 기록해야 파일 검토로 계산한다.

바이너리·비 UTF-8 자료는 자동으로 검토 완료나 안전으로 세지 않는다. 이미지 같은 비소스 자산은 `coverage.json.non_source_files[]`에 `root_id`, `path`, 원본 `sha256`, 비소스 판단 `rationale`, 실제 `reviewer`를 기록한다. 프로그램·라이브러리·바이트코드에는 대응 소스를 확보해 루트를 추가하고, 소스의 다른 인코딩에는 정적 디코더·줄 매핑을 준비한다. 해결하지 못하면 `partial` 또는 `blocked`다. 이 분류는 의미 판단이므로 검토자가 원시 자료에서 재확인한다.

심볼릭 링크는 연결 자체를 기록하고 대상이 등록된 루트에 속하는지 확인한다. 외부 소스를 가리키면 해당 소스를 확보해 루트로 등록한다. 끊어진 링크·접근 실패·지원하지 않는 파일 형식·잘린 목록은 공백이며 완료를 막는다. 제한된 `inventory --max-files` 출력은 편의 목록일 뿐 전체 스냅샷을 대신하지 않는다.

## 분석 전 기술 스택과 전체 취약점 유형을 준비한다

취약점 가설 분석 전에 `review-plan.json`을 준비한다. 준비 단계에서 소스·manifest·lockfile·설정·등록·배포 정의를 읽어 언어·런타임·프레임워크·버전·의존성·DB·프로토콜·작업·템플릿·직렬화·인프라·에이전트 구성요소를 식별한다. 각 스택 항목에 `id`, `name`, 확인한 `version` 또는 `null`, 실제 `source_refs`, 공식 보안 자료를 가리키는 `security_resources` ID 목록을 기록한다. ID는 확보한 `resources[]` 아티팩트와 연결돼야 한다. 불명 버전을 만들어 채우지 않는다.

전체 CWE XML과 스택별 공식 보안 문서·권고문·보안 요구사항을 확보한다. CWE Top-N, 특정 스캐너 룰, 익숙한 취약점 유형만으로 시작하지 않는다. 다음 명령은 공식 MITRE 전체 XML을 다운로드하고 모든 weakness 항목을 `pending`으로 생성한다. 이미 받은 XML/ZIP은 `--xml PATH --url OFFICIAL_URL`로 가져올 수 있다. 재가져오기는 적용 판단을 초기화하므로 기존 조사 노트를 보존한다.

전체 XML의 버전·원본 해시·항목 수는 조사 기록 밖의 [카탈로그 잠금 정보](cwe-catalogs.json)와 대조한다. 항목 일부를 삭제한 XML이나 조사자가 다시 적은 해시만으로 전체 목록이라고 인정하지 않는다. 새 릴리스가 나오면 키트 유지보수에서 공식 전체 파일을 별도로 내려받아 확인한 뒤 잠금 정보를 갱신한다. 분석 입력의 해시를 잠금 정보에 자동 등록하지 않는다. 미등록 버전·원본 불일치는 준비 실패로 남긴다.

```bash
python3 KIT_ROOT/scripts/workspace.py cwe --run RUN_ROOT
```

`weaknesses[]`에는 각 CWE와 각 스택 항목의 조합별로 `applicability`, `rationale`, `stack_ids`를 기록한다. 여러 스택에 같은 결론이 적용되면 한 행으로 묶고, 다르면 행을 나눈다. 적용되면 `applicable`, 해당 구조가 존재하지 않는 등의 근거가 있으면 `not-applicable`이다. “스캐너가 지원하지 않음”, “경고가 없음”, “심각도가 낮음”, “조사가 오래 걸림”은 비적용 근거가 아니다. 모든 조합에 판정이 있어야 하며 각 스택에는 실제 적용 취약점 분석이 있어야 한다.

적용 유형마다 조사할 입력·자산·통제·경로와 질문을 `coverage.json.units[]`에 먼저 만들고 `coverage_unit_ids`로 연결한다. 준비 단계에는 `unreviewed`·`partial` 단위를 사용할 수 있으나 완료에는 모두 `reviewed`여야 한다. 비적용 행도 `status=reviewed`, 명시적인 `coverage_unit_ids` 배열과 근거가 필요하다. 도구가 검출하지 못하는 업무 인가, 다중 테넌트, 순서·상태·동시성, 권한 결합, 프로세스·호스트·IAM 경계도 포함한다. 공개 분류에 없는 시스템 고유 가설은 별도 ID로 추가한다. 전체 공개 분류를 인지·대조한다는 요구를 알려지지 않은 모든 취약점을 발견했다는 보장으로 바꾸지 않는다. 발견 수나 심각도에 관계없이 적용 유형 전체를 검토한다.

준비가 끝나면 `phase`를 `ready`로 바꾸고 다음 검사를 통과한 후 본 분석에 들어간다. 새 스택이나 입력·권한 경계가 나오면 적용 판단과 계획을 보완한다.

```bash
python3 KIT_ROOT/scripts/check_kit.py --run RUN_ROOT --require-ready
```

## AI 모델과 CPU 도구의 역할

`review-plan.json.tasks[]`에 작업별 `id`, `executor`, `purpose`, `method`, `status`, `result_paths`를 기록한다. `executor`는 `ai` 또는 `cpu`다. 외부 코드를 실행하지 않는 로컬 헬퍼는 모델 API를 호출하지 않는다. 모델 호출은 호스트 에이전트의 계획·판단·위임 경로에서만 일어난다.

| CPU에서 수행할 일 | AI 모델이 판단할 일 |
| --- | --- |
| 전체 파일 열거, 스트리밍 해시·줄 수 계산, 변경 대조 | 조사 경계와 기술 스택의 의미·업무 자산·보안 요구사항 |
| manifest·lockfile·AST·등록·심볼·호출 관계 추출 | 전체 취약점 분류의 스택별 적용 여부와 필요한 추가 관점 |
| 전체 CWE 파싱·행 생성·누락 조합 검사 | 공격자 전제, 데이터·권한·상태 연결, 결함 가설·반증·영향 |
| 정적 데이터 흐름·규칙·정책 질의와 결과 정규화·중복 정리 | 프레임워크·업무 맥락에서 도구 결과와 모델링 공백 검토 |
| 소스 참조·해시·범위·완료 조건·출력 파일 일관성 검사 | 독립 반증, 후보 판정, 불확실성·검토 범위를 설명하는 보고서 |

반복 열거·검색·해시 계산을 파일마다 LLM 호출로 처리하지 않는다. 도구 결과를 묶어서 모델에 전달하되 원시 경로와 누락·오류를 보존한다. 모델이 고른 질문·질의를 CPU에서 실행하고 결과가 결론을 바꾸는지 모델이 검토하는 방식으로 반복한다. `method`에는 실제 도구·질의·명령 또는 모델 역할·방법을 쓰고, 실제 모델·옵션·호출량은 모델 사용 기록과 연결한다. 확인되지 않는 값은 미확인으로 둔다.

## 필요한 자료와 도구를 확보한다

환경에 필요한 자료·분석기가 없으면 공식 인터넷 배포처에서 내려받아 `RUN_ROOT/tools/` 또는 설치본의 `data_root/tools`(checkout은 `KIT_ROOT/.tools/`)에 준비한다. 이를 단순한 선택 기능 부족으로 넘기지 않는다. 전체 CWE·프레임워크 문서·권고문·공개 의존성 소스·정적 파서·분석기 등 현재 질문에 필요한 것을 확보하며, 무관한 모든 도구를 설치하지는 않는다.

필요 항목과 선택 이유를 먼저 `resources[]`에 등록하고 URL, 버전, 로컬 아티팩트·설치 manifest의 조사 폴더 기준 `path`, 전체 `sha256`, 실제 성공·실패를 남긴다. 공통 도구 캐시는 조사 폴더에 해당 출처·설치·해시 manifest를 보존해 연결한다. 자료가 누락되면 `pending`, 다운로드 성공은 `downloaded`, 기존 자료 확인은 `available`, 확보 실패는 `unavailable`로 기록한다. 필요 자료가 미확보 상태이면 준비·완료 검사를 통과하지 못한다.

네트워크·플랫폼·라이선스·로그인 문제면 다운로드 시도와 실패, 사용할 정적 대체 수단, 남은 질문을 기록한다. 비공개 운영 설정은 인터넷에서 얻을 수 있는 자료로 가장하지 않고 사용자에게 필요한 최소 자료를 요청한다. 대체 수단으로 같은 질문을 해결했다면 그 근거와 대체 결정을 보존하며 원래 실패를 성공으로 바꾸지 않는다. 다운로드와 로컬 도구 준비는 허용되지만 대상 설치 훅·빌드·애플리케이션 테스트·서비스·PoC 실행과 외부 공격은 포함하지 않는다.

## 후보와 보고서의 코드 근거

도구 경고·검색 힌트만 있는 단계는 `notes/`에 둔다. `findings/`에 등록하는 모든 후보에는 실제 코드의 `source_refs`를 하나 이상 붙인다. 루트·경로·정확한 줄·심볼·원본 전체 SHA-256·해당 코드가 직접 지지하는 좁은 주장을 함께 기록한다. 근거가 있다는 사실과 결함으로 확정됐다는 판단은 구분한다.

소스로 지지되는 연결에는 `chain[].evidence_indices`로 해당 참조를 연결한다. 후보 보고서에는 공격자가 통제하는 입력·초기 권한, 진입점부터 민감 동작까지의 코드 연결, 실패한 통제, 보호 계층·반증, 성립 조건·미확인을 작성한다. 실제 코드를 최소한으로 발췌해 설명하고 비밀값은 마스킹한다. 확인하지 못한 연결을 코드 사실로 쓰지 않는다. 기각한 후보도 기각한 코드·통제 근거를 남긴다.

`REPORT.md`에는 후보 ID, 코드 경로·줄·심볼·파일 전체 해시, 코드 발췌와 해석을 포함한다. 자동 검사기는 ID·경로·해시 포함과 참조 무결성을 확인하며, 코드가 주장을 지지하는지는 AI와 실제 검토자가 판단한다. 스캐너 등급·모델 확신·검사 통과를 그 판단의 대체물로 삼지 않는다.

## 완료 검사

다음을 모두 충족해야 `state.json.status=complete`를 사용할 수 있다.

- 모든 루트의 전체 목록과 현재 원본 바이트가 일치하며 접근 실패·미등록 링크·미해결 소스 형식이 없다.
- 대상 텍스트 파일과 줄의 검토 기록이 100%이며 모든 필수 보안 경로·검토 단위가 `reviewed`다. 제외로 분모를 줄이지 않는다.
- 스택과 전체 CWE의 적용 판단이 준비됐고, 모든 적용 유형이 완료된 검토 단위와 연결돼 있다.
- AI·CPU 작업에 실제 완료 결과가 있고 필요한 자료·도구 확보가 끝났다.
- 판단 전 후보·핵심 근거가 빠진 후보가 남지 않고, 보고한 후보의 지지·반증·조건·최종 검토와 코드 근거가 보고서에 반영됐다.
- 실제 완료 보고서가 있고 필수 `next_actions`·`blockers`가 남지 않는다.

배포 미확정 조건을 정확히 분리한 `conditional` 결론은 코드 검토 완료와 양립할 수 있다. 반면 핵심 코드 연결이 미검토라면 `needs-evidence`이며 완료할 수 없다. 예산 소진은 `partial`, 필요한 자료 부족으로 진행 불능이면 `blocked`로 전달하고 남은 작업을 보존한다. 심각도가 낮다는 이유로 남은 대상을 생략하지 않는다.

```bash
python3 KIT_ROOT/scripts/check_kit.py --run RUN_ROOT
```

현재 소스가 바뀌거나 루트가 추가되면 `workspace.py snapshot` 또는 `add-root`로 목록을 갱신한다. 이전 목록은 `evidence/inventory-history/`에 보존되고 준비 상태가 해제된다. 기존 참조를 새 바이트에 재사용하지 말고 변경 구간·호출 관계·영향받는 유형을 재검토한다. 과거 조사에는 `snapshot`과 새 `review-plan.json`을 준비하며, 기록이 없는 이전 검토를 자동으로 완료 처리하지 않는다.

이 검사는 선언된 검토 기록의 전수성·연결·무결성을 검사한다. 실제로 모든 구간을 이해했는지, 모든 스택·경로를 정확히 식별했는지, 분류·비소스 판단이 맞는지와 알려지지 않은 결함까지 발견했는지는 기계적 형식 검사로 증명하지 않는다. 주 조사자와 독립 검토자는 이 의미적 근거를 확인하고 실제 검토의 한계를 보고한다.
