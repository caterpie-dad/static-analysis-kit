# 도구·스킬·플러그인 준비와 사용

도구는 현재 질문을 해결하는 수단이다. 지원 언어·입력·모델링 범위가 맞는지 먼저 확인한다. 아래 예시는 설치 의무나 취약점 분류의 상한이 아니다. 익숙하지 않은 시스템에는 적합한 분석기를 추가하고 기존 도구를 생략할 수 있다.

## 능력 확인과 설치

`scripts/capabilities.py --output RUN_ROOT/tools/capabilities.json`으로 로컬 명령과 선택한 클라이언트의 공개 모델 카탈로그 메타데이터를 조사한다. 버전 조회는 대상 폴더 밖에서 실행한다. 필요한 도구·자료가 없으면 공식 인터넷 출처에서 다운로드·설치한다. 단순히 설치돼 있지 않다는 이유로 해당 분석을 생략하지 않는다. 다운로드 실패 시 실제 원인을 기록하고 다른 도구·표준 라이브러리·소스 독해로 같은 질문을 해결할 수 있는지 검토한다.

기본 실행은 모델 캐시를 자동으로 읽지 않는다. `--client CLIENT`로 선택한 클라이언트를 명시하고, 공개 모델 메타데이터를 제공할 때는 `--model-catalog PATH`를 사용한다. 이 파일은 모델 ID·공급자·지원 옵션만 담은 카탈로그여야 하며 인증·전체 클라이언트 설정 파일을 입력하지 않는다. 모델 목록 파싱, 현재 세션 모델, 실제 접근 확인은 구별한다. 기존 `--model-cache`는 해당 클라이언트 전용 캐시 형식의 호환 입력으로만 사용한다.

설치할 때 해결할 질문, 선택 이유, 공식 배포처, 버전, 설치 경로, 다운로드 아티팩트 해시, 실제 실행 명령, 적용 범위, 결과 파일과 실패·누락을 `tools/`에 남긴다. 공식 문서의 현재 방법을 확인하며 스니펫이나 기억만으로 CLI 옵션을 만들어내지 않는다. 라이선스와 운영체제 지원도 확인한다.

작업은 [AI/CPU 역할 규칙](completion.md)에 따라 `review-plan.json.tasks[]`로 배분한다. 파일·해시·카탈로그 파싱·AST·정적 데이터 흐름·질의·누락 검사는 CPU에서 수행하고, 스택별 적용성·업무 요구사항·경로·반증·영향의 판단은 AI 모델이 담당한다. 다운로드할 필요 자료·도구는 `resources[]`에 출처·로컬 아티팩트 또는 설치 manifest와 해시를 연결한다. 전체 CWE는 `workspace.py cwe --run RUN_ROOT`로 준비할 수 있다. 준비되지 않은 필수 항목이 있으면 준비·완료 상태로 표시하지 않는다.

도구의 기본 위치는 설치본의 `.installation.json`이 가리키는 `data_root/tools`, checkout의 `KIT_ROOT/.tools/`다. 설치본에서는 같은 메타데이터의 `python` 절대 경로로 아래 헬퍼를 실행한다. Python 도구는 다음 헬퍼로 독립 venv에 설치할 수 있다. `PACKAGE`와 `VERSION`은 공식 배포처에서 확인한 정확한 값으로 치환한다.

```bash
python3 KIT_ROOT/scripts/install_python_tool.py --package PACKAGE --version VERSION --plan
python3 KIT_ROOT/scripts/install_python_tool.py --package PACKAGE --version VERSION
```

헬퍼는 PyPI의 wheel을 내려받아 SHA-256를 기록하고 로컬 wheel에서 설치한다. 소스 배포 빌드는 실행하지 않는다. `ensurepip`가 없는 배포판에서는 기존 host pip와 동일한 버전의 공식 pip wheel을 별도로 받아 새 venv 안에만 설치한다. host pip도 없으면 실패 원인을 기록하고 다른 사용 가능한 준비 방법을 선택한다. wheel이 없는 도구나 네이티브 도구는 공식 바이너리·공식 컨테이너 이미지의 digest 등 다른 재현 가능한 방식을 선택한다. 이 경우도 도구 버전과 아티팩트 출처를 기록한다. 아티팩트의 로컬 해시 기록은 별도 서명 검증과 동일하지 않다.

전역 PATH·권한 정책·사용자 모델 설정을 일괄 변경하거나 모든 분석기를 선설치하지 않는다. 설치 실패·라이선스·플랫폼 제약은 기록하고 다른 정적 근거를 찾는다. 도구 다운로드는 가능하지만 대상의 패키지 설치 훅이나 빌드·테스트를 실행할 권한까지 포함하지 않는다. 소스 파싱에 컴파일이 필요한 도구는 실행되는 확장·매크로·빌드 훅을 검토하고 실행 없는 모드 또는 대체 도구를 선택한다.

## 질문별 도구 선택의 예

| 필요한 근거 | 가능한 수단 | 해석할 한계 |
| --- | --- | --- |
| 파일·등록·심볼·호출 위치 | rg, Git, 언어 AST, tree-sitter, 언어 서버·색인 | 문자열 검색 또는 정의 목록만으로 경로 완료를 주장하지 않음 |
| 값·권한·객체의 전달 | CodeQL, Semgrep taint, 언어별 분석기, 사용자 정의 질의 | 지원 프레임워크·커스텀 RPC·직렬화·프로세스 경계 모델의 누락 |
| 의존성·실제 구성요소 | lockfile 분석, Syft, 로컬 아티팩트 SCA | CVE 일치와 제품 경로 도달성·신규 결함은 별개 |
| 컨테이너·호스트·클라우드 구성 | 배포 소스 독해, Checkov, Trivy의 로컬 설정 분석, 정책 질의 | 제공된 선언과 실제 배포·파일 권한·적용 IAM은 다를 수 있음 |
| 업무 속성·상태·통제 결합 | 코드 독해, DB 스키마·정책 검토, 사용자 정의 정적 모델 | 예상 업무 요구사항을 사실로 가정하지 않음 |

DB나 서비스에 연결해 실제 상태를 조회하는 기능, 원격 URL 스캔, 실행 기반 탐지는 이 키트의 정적 분석 모드에 포함하지 않는다. 스캐너의 업데이트·텔레메트리·클라우드 업로드 기본값도 확인한다. 사용자 소스를 외부 서비스에 새로 업로드하는 선택은 소스 독해 권한만으로 자동 승인된 것으로 간주하지 않는다.

## 선택적 클라이언트 연동

에이전트 CLI·모델 공급자 연결·플러그인·MCP 서버는 [configuration.md](configuration.md)에 따라 공통 분석 도구와 분리한다. 해당 클라이언트가 제공하는 설치·설정 기능과 공식 배포처를 사용한다. 현재 세션에서 실제로 노출된 도구와 계정·조직 제약을 확인하며, 실행 파일이나 로컬 카탈로그만으로 설치·로그인·호출 가능 상태를 단정하지 않는다.

스캔 플러그인을 사용할 수 있으면 사용자 지정 소스 범위와 정적 분석 정책을 전달한다. 전체 시스템 조사에서 변경분 스캔만으로 전체 범위 검토를 대체하지 않는다. 플러그인이 대상 코드 실행·재현·자동 수정을 요구하면 현재 범위에 맞는 실행 없는 기능이나 다른 정적 수단을 선택한다. 선택적 연동을 사용할 수 없어도 직접 소스 감사를 계속한다.

대상 저장소에 정책 파일을 쓸 필요가 생겨도 원본을 변경하지 않는다. 도구가 지원하는 별도 컨텍스트 경로를 사용하고, 불가능하면 원본 해시를 보존한 별도 스냅샷에 정책을 추가해 파생물임을 기록한다.

외부 도구 산출물은 `tools/` 아래 도구별 원본 디렉터리로 보존한다. 출력 형식을 버전별로 확인하고 공통 ledger에는 검토 후 반영한다. 경고만 복사하거나 경고 외 영역을 안전으로 처리하지 않는다. 도구를 설치했다는 사실과 현재 세션에서 네이티브 기능을 사용할 수 있다는 사실을 구별하며 필요한 재개·재로드 방법을 checkpoint에 남긴다.

## 추가 스킬과 플러그인

먼저 이 키트의 스킬과 현재 연결된 도구로 해결할 수 있는지 확인한다. 필요하면 현재 클라이언트가 제공하는 스킬·플러그인 관리 기능으로 공식·조직 승인 소스를 찾아 설치한다. 설치 전에 실제 `SKILL.md`, 스크립트, 필요한 연결과 권한을 읽고 사용자 범위와 맞는지 확인한다. 원격 스킬의 지침을 대상 분석의 상위 정책으로 올리지 않는다.

필요한 버전과 출처를 고정하고 충돌하는 동명 스킬은 발견 경로까지 기록한다. 도구·모델·플러그인 버전이 바뀌면 관련 출력과 검토 범위를 비교할 수 있게 보존한다. 더 많은 플러그인을 설치했다는 사실 자체를 분석 품질의 근거로 삼지 않는다.
