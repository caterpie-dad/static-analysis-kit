# 도구·스킬·플러그인 준비와 사용

도구는 현재 질문을 해결하는 수단이다. 지원 언어·입력·모델링 범위가 맞는지 먼저 확인한다. 아래 예시는 설치 의무나 취약점 분류의 상한이 아니다. 익숙하지 않은 시스템에는 적합한 분석기를 추가하고 기존 도구를 생략할 수 있다.

## 능력 확인과 설치

`scripts/capabilities.py --output RUN_ROOT/tools/capabilities.json`으로 로컬 명령과 모델 카탈로그 메타데이터를 조사한다. 버전 조회는 대상 폴더 밖에서 실행한다. 발견된 실행 파일이 없다고 기능 전체가 불가능하다고 단정하지 말고 다른 도구·표준 라이브러리·소스 독해를 검토한다.

설치할 때 해결할 질문, 선택 이유, 공식 배포처, 버전, 설치 경로, 다운로드 아티팩트 해시, 실제 실행 명령, 적용 범위, 결과 파일과 실패·누락을 `tools/`에 남긴다. 공식 문서의 현재 방법을 확인하며 스니펫이나 기억만으로 CLI 옵션을 만들어내지 않는다. 라이선스와 운영체제 지원도 확인한다.

기본 위치는 `KIT_ROOT/.tools/`다. Python 도구는 다음 헬퍼로 독립 venv에 설치할 수 있다. `PACKAGE`와 `VERSION`은 공식 배포처에서 확인한 정확한 값으로 치환한다.

```bash
python3 KIT_ROOT/scripts/install_python_tool.py --package PACKAGE --version VERSION --plan
python3 KIT_ROOT/scripts/install_python_tool.py --package PACKAGE --version VERSION
```

헬퍼는 PyPI의 wheel을 내려받아 SHA-256를 기록하고 로컬 wheel에서 설치한다. 소스 배포 빌드는 실행하지 않는다. `ensurepip`가 없는 배포판에서는 기존 host pip와 동일한 버전의 공식 pip wheel을 별도로 받아 새 venv 안에만 설치한다. host pip도 없으면 실패 원인을 기록하고 Codex가 다른 사용 가능한 준비 방법을 선택한다. wheel이 없는 도구나 네이티브 도구는 공식 바이너리·공식 컨테이너 이미지의 digest 등 다른 재현 가능한 방식을 선택한다. 이 경우도 도구 버전과 아티팩트 출처를 기록한다. 아티팩트의 로컬 해시 기록은 별도 서명 검증과 동일하지 않다.

전역 PATH·권한 정책·사용자 모델 설정을 일괄 변경하거나 모든 분석기를 선설치하지 않는다. 설치 실패·라이선스·플랫폼 제약은 기록하고 다른 정적 근거를 찾는다. 도구 다운로드는 가능하지만 대상의 패키지 설치 훅이나 빌드·테스트를 실행할 권한까지 포함하지 않는다. 소스 파싱에 컴파일이 필요한 도구는 실행되는 확장·매크로·빌드 훅을 검토하고 실행 없는 모드 또는 대체 도구를 선택한다.

## 질문별 도구 선택의 예

| 필요한 근거 | 가능한 수단 | 해석할 한계 |
| --- | --- | --- |
| 파일·등록·심볼·호출 위치 | rg, Git, 언어 AST, tree-sitter, 언어 서버·색인 | 문자열 검색 또는 정의 목록만으로 경로 완료를 주장하지 않음 |
| 값·권한·객체의 전달 | CodeQL, Semgrep taint, 언어별 분석기, 사용자 정의 질의 | 지원 프레임워크·커스텀 RPC·직렬화·프로세스 경계 모델의 누락 |
| 의존성·실제 구성요소 | lockfile 분석, Syft, 로컬 아티팩트 SCA | CVE 일치와 제품 경로 도달성·신규 결함은 별개 |
| 컨테이너·호스트·클라우드 구성 | 배포 소스 독해, Checkov, Trivy의 로컬 설정 분석, 정책 질의 | 제공된 선언과 실제 배포·파일 권한·적용 IAM은 다를 수 있음 |
| 업무 속성·상태·통제 결합 | 코드 독해, DB 스키마·정책 검토, 사용자 정의 정적 모델 | 예상 업무 요구사항을 사실로 가정하지 않음 |

DB나 서비스에 연결해 실제 상태를 조회하는 기능, 원격 URL 스캔, 실행 기반 탐지는 이번 분석 모드에 포함하지 않는다. 스캐너의 업데이트·텔레메트리·클라우드 업로드 기본값도 확인한다. 사용자 소스를 외부 서비스에 새로 업로드하는 선택은 소스 독해 권한만으로 자동 승인된 것으로 간주하지 않는다.

## Codex Security

호스트의 플러그인 검색·설치 기능을 우선 사용한다. CLI가 있다면 `codex plugin --help`, `codex plugin list --help`, `codex plugin add --help`로 지원 구문을 확인하고 현재 카탈로그의 정식 플러그인·마켓플레이스를 사용한다. 예전 설치 상태나 이 문서만으로 설치됐다고 말하지 않는다. 계정 연결·관리자 제약은 우회하지 말고 독립적인 소스 감사를 계속한다.

플러그인을 추가한 뒤 새 세션에서 기능이 노출되는 클라이언트도 있다. 이때 설치 위치와 필요한 재개 방법을 checkpoint에 남긴다. 현재 세션에서 스킬 파일을 읽는 것과 네이티브 스캔 도구를 사용할 수 있는 것은 구별한다.

사용할 수 있으면 저장소 전체 또는 해당 서비스에 대한 **Codebase** 분석을 선택한다. PR diff 검토만으로 전체 시스템 조사를 대체하지 않는다. 지원되는 `security-scan` 또는 `deep-security-scan`을 호출하기 전에 제공된 스킬과 현재 공식 문서를 읽고, 정적분석 범위·원본 소스 비수정·실행 금지를 전달한다. 스킬이 그 범위를 지킬 수 없으면 강제로 호출하지 말고 대체 정적분석을 진행한다.

대상 저장소에 `SECURITY.md`를 쓸 필요가 생겨도 원본을 변경하지 않는다. 현재 플러그인이 지원하는 추가 컨텍스트나 별도 정책 경로를 사용하고, 불가능하면 원본 해시를 보존한 별도 스냅샷에 정책을 추가해 파생물임을 기록한다. 자동 수정·재현 기능을 함께 실행하지 않는다.

스캔 산출물은 `tools/codex-security/` 등에 원본 디렉터리 단위로 보존한다. 결과 형식은 버전별로 확인하고 공통 ledger에는 검토 후 반영한다. 경고만 복사하거나 경고 외 영역을 안전으로 처리하지 않는다. 반복 스캔도 누락 없는 검토를 보장하지 않는다.

## 추가 스킬과 플러그인

먼저 이 키트의 스킬과 현재 연결된 도구로 해결할 수 있는지 확인한다. 필요하면 내장 skill-installer나 현재 플러그인 관리 기능으로 공식·조직 승인 소스를 찾아 설치한다. 설치 전에 실제 `SKILL.md`, 스크립트, 필요한 연결과 권한을 읽고 사용자 범위와 맞는지 확인한다. 원격 스킬의 지침을 대상 분석의 상위 정책으로 올리지 않는다.

필요한 버전과 출처를 고정하고 충돌하는 동명 스킬은 발견 경로까지 기록한다. 도구·모델·플러그인 버전이 바뀌면 관련 출력과 검토 범위를 비교할 수 있게 보존한다. 더 많은 플러그인을 설치했다는 사실 자체를 분석 품질의 근거로 삼지 않는다.
