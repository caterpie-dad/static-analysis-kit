# 정적 보안 조사 방법

이 방법은 특정 언어·프레임워크·배포 형태에 종속되지 않는다. 취약점 규칙 목록 통과가 목적이 아니다. 소스·설정·정책·배포 정의를 근거로 시스템이 지켜야 할 보안 성질을 찾고, 그 성질이 깨질 수 있는 경로를 조사한다. 아래 관점과 예시는 출발점이며 조사 범위의 완전성을 보장하지 않는다.

## 1. 범위와 근거를 먼저 고정한다

- 허용된 소스 루트마다 `root_id`를 부여하고 경로, 리비전 또는 스냅샷, 접근 제한을 기록한다. 외부 의존성이나 생성물이 빠져 있으면 별도 공백으로 남긴다.
- 코드뿐 아니라 서비스 정의, 실행 사용자, 파일 권한 설정, 컨테이너·오케스트레이션 정의, IAM 정책, 데이터 스키마, 빌드·배포 흐름, 관리 인터페이스를 찾아 시스템에 실제로 관련된 자료를 고른다.
- 문서가 말하는 설계, 코드가 구현한 동작, 배포 시에만 정해지는 값을 구분한다. 소스에서 배포 상태를 단정하지 않는다.
- 저장소 전체를 목록화한 사실, 파일을 읽은 사실, 의미와 경로를 검토한 사실은 각각 기록한다. 목록에 있다는 이유로 검토 완료로 표시하지 않는다.

조사는 정적 읽기와 로컬 분석 산출물 작성에 한정한다. 대상 프로그램 실행, 서비스 호출, 원격 네트워크 탐색, 취약점 재현, 자격 증명 사용, 운영 환경 변경은 이 방법의 범위 밖이다. 로컬 소스·설정 스캐너는 사용할 수 있다. 비밀값을 발견해도 사용하거나 보고서에 원문을 복사하지 않는다.

## 2. 구조와 보안 불변조건을 만든다

실제 자료에 맞춰 다음을 간결한 표나 그래프로 표현한다.

- 구성 요소와 배포 위치, 호출·메시지·파일·데이터 흐름, 동기·비동기 실행 및 관리 경로
- 외부 사용자, 내부 서비스, 운영자, 워크로드 등 행위자와 이들이 통제할 수 있는 입력·상태·설정
- 보호할 자산과 불변조건: 예를 들어 소유자가 다른 데이터를 수정하지 못함, 서명된 산출물이 바뀌지 않음, 낮은 권한의 작업이 호스트 권한을 얻지 못함
- 인증·인가·검증·격리·암호화·감사 등 통제가 적용되는 위치와 적용되지 않는 위치

불변조건은 시스템의 목적과 근거에서 도출한다. 모든 시스템에 같은 자산이나 경계를 가정하지 않는다. 경계가 분명하지 않으면 하나의 신뢰 영역으로 합치지 말고 미확정 경계로 남긴다.

## 3. 네 관점을 독립적으로 적용한다

한 관점의 결과만으로 다른 관점의 검토를 생략하지 않는다. 각 관점에서 새로운 경로와 반례를 발견하면 구조 모델과 가설을 갱신한다.

| 관점 | 조사 질문 | 가능한 출발점의 예시 |
| --- | --- | --- |
| 진입점 → 흐름 | 누가 무엇을 통제하며, 그 값이나 권한이 어디까지 전달되는가? | 요청, CLI, 메시지, 파일, 플러그인, 작업 큐, 배포 설정에서 민감한 동작까지의 변환·검증 |
| 자산 → 불변조건 | 무엇이 보호되어야 하며, 이를 변경·노출할 수 있는 모든 경로는 무엇인가? | 데이터 소유권, 테넌트 구분, 자격 증명, 산출물 무결성, 관리 상태의 읽기·쓰기·삭제·복구 경로 |
| 능력 → 영향 | 작은 초기 능력이 어떤 경계와 조건을 거쳐 더 큰 능력으로 바뀌는가? | 작업 실행 권한에서 서비스 계정, 컨테이너에서 호스트, 한 워크로드에서 다른 자산·네트워크·계정으로 이어지는 조건 |
| 알려진 패턴 → 맥락 | 익숙한 위험 패턴이 실제 보안 성질을 깨는가? 반대로 정상 용도인가? | 경로 해석, 역직렬화, 권한 위임, 비밀 전달, 동시성, 캐시, 정책 결합과 기본값의 맥락 |

패턴 검색 결과는 탐색 단서다. 패턴 일치가 결함을 증명하지 않으며, 패턴 불일치가 안전을 증명하지 않는다. 가용한 설정과 소스에 따라 호스트·컨테이너·IAM 경계, 데이터 무결성·유출, 권한 상승·횡적 이동을 검토하되, 이 예시들을 고정된 취약점 분류나 통과 조건으로 사용하지 않는다.

## 4. 가설을 검증 가능한 문장으로 좁힌다

가설에는 공격자, 초기 능력, 필요한 조건, 깨지는 불변조건, 후보 경로를 적는다. 예: “역할 A가 객체 식별자를 지정할 수 있고 저장 계층에서도 소유권을 검사하지 않는다면 다른 소유자의 데이터를 바꿀 수 있다.” 넓은 주장은 작은 주장으로 나누고 각각의 근거와 반증 가능성을 찾는다.

우선순위는 예상 영향뿐 아니라 근거의 강도, 조사 가능한 경로, 미확정 경계의 중요도를 함께 고려한다. 눈에 띄는 API나 심각도 이름만 따라가지 않는다. 새 근거가 나오면 우선순위와 가설을 수정한다.

각 가설은 다음 순서로 검토한다.

1. 진입 지점과 초기 권한을 소스에서 찾는다.
2. 호출, 데이터 변환, 저장·재사용, 비동기 전달, 권한 위임을 단계별로 연결한다.
3. 민감한 동작에서 거꾸로 추적해 필수 호출자, 전처리, 중앙 정책, 저장 계층 검사 등 우회 가정을 깨는 통제를 찾는다.
4. 적용 범위가 다른 분기·설정·역할·오류 처리·실패 시 동작을 비교한다. 눈에 보이는 검사 하나가 모든 경로에 적용된다고 추정하지 않는다.
5. 결함 자체, 도달 가능성, 영향 확장을 각각 판단한다. 증거가 없는 연결은 조건부로 남긴다.

## 5. 경계 전환을 간선별로 기록한다

여러 단계의 공격 가능성은 하나의 문장으로 압축하지 않는다. `chain[]`의 각 단계에는 다음 내용을 구조화해 담는다. 구체적인 필드 계약은 키트의 finding 스키마를 따른다.

| 내용 | 기록할 사항 |
| --- | --- |
| 시작과 끝 | 구성 요소·실행 문맥, 이동하는 값 또는 수행 동작 |
| 행위자와 권한 | 전환 전후의 신원·역할·능력, 입력이나 상태를 통제하는 주체 |
| 경계와 조건 | 신뢰·테넌트·프로세스·호스트·컨테이너·계정 경계, 필요한 설정과 선행 상태 |
| 통제와 반증 | 검증·인가·격리 위치, 흐름을 막는 근거, 통제의 적용 범위 |
| 지지 근거와 공백 | 해당 주장을 뒷받침하는 `source_refs`, 불명확한 호출자·설정·런타임 속성 |

앞 단계의 출력 능력이 다음 단계의 입력 조건을 충족하는지 확인한다. 같은 값·신원·권한이 유지된다는 가정도 검토 대상이다. 예를 들어 소스에서 민감한 파일 접근 가능성이 보이더라도 실제 마운트, 실행 UID, 파일 권한, 정책을 모르면 호스트 장악까지 확장하지 않는다. 누락된 간선을 그럴듯한 설명으로 메우지 않는다.

## 6. 반증, 기록, 종료

가설마다 이를 무효화하거나 범위를 줄이는 근거를 적극적으로 찾고 `counterevidence[]`에 남긴다. 통제가 존재한다는 사실과 그 통제가 해당 경로에서 유효하다는 판단을 구분한다. 반증으로 기각한 가설도 이유와 근거를 보존한다.

결과는 [근거 규칙](evidence.md)에 따라 기록한다. 코드만으로도 특정 검사 누락이나 불변조건 위반을 충분히 입증할 수 있다. 이때 결함은 `source-supported`로 판단할 수 있지만 실행 확인을 뜻하지 않는다. 별도 배포 조건이나 추가 권한이 필요한 경로·영향은 조건부로 서술한다.

조사 종료 시에는 검토한 범위와 남은 공백, 중단 사유, 가장 가치 있는 다음 정적 조사 행동을 명시한다. 발견 수가 0이거나 특정 패턴 검색을 끝냈다는 이유로 안전 또는 완전성을 선언하지 않는다.
