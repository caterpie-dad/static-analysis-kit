# 에이전트 안에서 키트 사용과 모델 설정

이 문서는 키트를 불러온 에이전트가 읽는다. 일반 사용자는 클라이언트를 실행해 스킬 이름과 자연어 요청만 입력한다. 사용자에게 TOML·JSON 작성, 내부 헬퍼 실행, 설치기 재실행을 요구하지 않는다.

## 호출과 요청 구분

| 클라이언트 | 명시적 호출 |
| --- | --- |
| Codex | `$static-analysis-kit` 또는 `/skills`에서 스킬 선택 |
| Claude Code | `/static-analysis-kit` |
| Mistral Vibe | `/static-analysis-kit` |
| OpenCode | `static-analysis-kit 스킬을 사용해줘` |

기존 `system-static-analysis` 이름도 호환 진입점으로 유지한다. Codex에 임의의 `/static-analysis-kit` 내장 명령을 등록했다고 주장하지 않는다. `$`는 키트 스킬을 불러오고 `/model`은 Codex 자체의 주 모델 선택 화면이다.

단독 호출에는 현재 설정과 가능한 요청을 짧게 보여준다. 예를 들어 “설정 보여줘 / 역할별 모델 바꿔줘 / 이 경로 분석해줘 / 이전 조사 이어가줘”다. 설정 요청만으로 소스 분석을 시작하거나 대상 경로를 질문하지 않는다. 기본 모델을 유지하면 클라이언트의 상속·기본값을 따른다고 설명한다. Luna·Sol 등을 키트 기본 배정으로 간주하지 않는다.

설치 스킬에 명시된 `KIT_ROOT`, 실행기, 현재 클라이언트를 사용한다. 저장소에서 직접 스킬을 불렀으면 현재 호스트를 확인하고 해당 클라이언트의 설치 기록을 찾는다. 여러 클라이언트가 설치돼 있어도 현재 클라이언트를 대상으로 하며 사용자 지정 없이 다른 CLI를 실행하지 않는다. 설치 기록이 없을 때만 한 줄 설치를 안내한다.

## 현재 설정과 사용 가능한 모델

설정 작업과 분석 시작 시 에이전트가 내부적으로 다음을 실행한다. `PYTHON`은 설치 스킬 또는 `.installation.json`의 실행기다. 경로·인수는 안전하게 인용하거나 argv로 전달한다.

```text
PYTHON KIT_ROOT/scripts/manage.py models show --client CLIENT
```

주 조사자·inventory·analyst·reviewer의 요청 모델과 주 세션의 실제 관찰 모델을 나눠 표로 보여준다. `null`은 상속 또는 미확인이며 임의의 모델 ID로 채우지 않는다. `max_concurrent`는 역할 수나 모델 종류 수가 아닌 위임 동시성 요청 한도다.

사용 가능한 모델은 현재 호스트가 제공하는 모델 목록·선택 화면·공개 카탈로그 메타데이터에서 확인한다. 캐시·설정된 별칭과 실제 호출 접근은 구분한다. 자격증명 저장소나 전체 클라이언트 설정을 읽어 목록을 추출하지 않는다. 호스트가 목록을 제공하지 않으면 Codex의 `/model`처럼 현재 클라이언트의 모델 선택 화면을 안내하고 선택을 받는다. 다른 터미널 명령이나 사용자가 만든 설정 파일을 요구하지 않는다.

“Terra”, “Astra”, “GPT Cyber”, “Mistral Large 4” 등의 표시 이름은 실제 계정·현재 공급자의 정확한 모델 참조 또는 등록 프리셋으로 해석한다. 유일하게 확인되면 진행하고 버전·공급자 후보가 여러 개면 그 선택만 질문한다. 존재·접근을 확인하지 않은 ID나 별칭을 만들어내지 않는다. 설정을 저장하기 위해 유료 모델 시험 호출은 하지 않는다.

## 자연어 선택 저장

에이전트가 선택을 다음 내부 JSON 계약으로 바꾼다. 모델 참조는 호스트에서 확인하거나 사용자가 명시한 값이다. 예시의 `chosen-model`은 실제 참조로 바꾼다. 사용자는 이 계약을 알 필요가 없다.

| 사용자 의도 | 내부 요청 |
| --- | --- |
| 모든 분석 역할을 한 모델로 | `{"single_model":"chosen-model"}` |
| 검토 역할만 변경 | `{"roles":{"reviewer":"chosen-model"}}` |
| 주 조사자 모델 지정 | `{"main_model":"chosen-model"}` |
| 역할별 지정 | `{"roles":{"inventory":"model-a","analyst":"model-b","reviewer":"model-c"}}` |
| 기본 상속으로 복원 | `{"inherit":true}` |
| 동시 위임 요청 한도 변경 | `{"max_concurrent":2}` |

역할별 네이티브 추론 옵션은 `{"roles":{"reviewer":{"model":"chosen-model","options":{"model_reasoning_effort":"high"}}}}`처럼 전달할 수 있다. 지원 옵션은 해당 어댑터가 검사한다. 사용자가 요청하지 않은 모델·추론 등급 변경을 추가하지 않는다. “현재 모델 하나만”은 호스트에서 현재 모델의 정확한 참조를 확인해 single 모드로 고정하며, `inherit`를 단일 모델 보장으로 취급하지 않는다.

헬퍼는 stdin 또는 임시 요청 파일을 받는다. 요청을 shell 문자열에 직접 끼워 넣지 않는다. 임시 파일은 도구가 지원하는 구조화된 쓰기로 만들고 필요가 끝나면 제거한다.

```text
PYTHON KIT_ROOT/scripts/manage.py models set --client CLIENT --request -
PYTHON KIT_ROOT/scripts/manage.py models reset --client CLIENT
```

저장은 설치 소유권·기존 해시를 검증한 transaction으로 네이티브 역할과 설치 설정을 함께 갱신한다. 원본 소스, 설치 패키지, 사용자의 전체 모델·인증 설정은 변경하지 않는다. 충돌이면 실제 이유를 설명하며 사용자 파일을 덮어쓰지 않는다. 업데이트 후에도 저장된 배정을 유지한다.

완료 응답에는 **설정 저장 / 네이티브 역할 파일 갱신 / 현재 세션 적용 / 계정 접근 확인**을 구별한다. 관리 헬퍼는 모델을 호출하거나 주 세션을 전환하지 않는다. 저장만으로 “모두 해당 모델로 실행 중”이라고 말하지 않는다.

## 현재 세션과 다음 분석에 적용

주 세션 모델은 호스트가 관리한다. 호스트에 현재 대화의 모델을 전환하는 공식 기능이 실제 노출돼 있으면 사용자 선택에 따라 사용한다. 노출되지 않은 경우 Codex에서는 같은 화면에서 `/model`로 선택하게 안내한다. 다른 클라이언트도 해당 호스트의 모델 선택 기능을 사용한다. 저장된 주 모델 의도는 다음 분석 시작 때도 확인한다. 주 모델 선택을 위해 전체 사용자 기본 설정을 몰래 바꾸지 않는다.

하위 역할은 갱신된 네이티브 정의를 다시 로드하거나 현재 위임 API가 지원하는 명시적 모델 인수를 사용한다. 같은 세션의 모델별 위임 지원·허용 목록·공급자 경계를 확인한다. 호스트가 선택 모델을 표현하지 못하면 그 역할을 다른 모델로 수행한 척하지 말고 호스트 재로딩·새 세션 등 실제 필요한 동작을 안내한다.

에이전트는 분석 시작과 모델 변경 뒤 내부적으로 다음 검사로 요청과 관찰을 대조할 수 있다. 관찰이 제공되지 않으면 주 모델 일치는 미확인이며 명시적 주 모델을 요구하는 분석은 준비 완료로 표시하지 않는다.

```text
PYTHON KIT_ROOT/scripts/manage.py models check --client CLIENT --observed-main MODEL_REF
```

호스트의 모델 목록이 있을 때만 `--available-model MODEL_REF`를 반복해 전달한다. 실제 목록이 없으면 이 인수를 만들어 넣지 않는다. `analysis_can_start=false`이면 해당 불일치를 먼저 해결하고 요청한 모델이 적용됐다고 보고하지 않는다. `true`는 전달된 모델 제약의 기계적 검사 결과이며 현재 역할 로딩·계정 접근을 증명하지 않는다. 명시적 주 모델 제약이 없으면 일치 여부는 `null`이다. 실제 역할 활성화는 호스트에서 별도 확인한다.

“한 모델만”이라는 요청은 분석 네 역할뿐 아니라 호스트의 요약·제목·승인 등 보조 호출도 함께 확인한다. 예를 들어 Vibe의 `utility_models.title`, `utility_models.smart_approve`와 별도 compaction 모델 설정을 확인하고 호스트가 지원하는 설정 방법을 안내한다. 키트의 역할 배정만으로 모든 호스트 내부 호출이 한 모델이라고 보장하지 않는다. 확인 불가·정책 제한이면 그 적용 범위를 명확히 남긴다.

분석을 시작하면 [model-routing.md](model-routing.md)에 따라 저장된 설정과 실제 위임 모델을 조사 기록에 남긴다. 재설정으로 기존 분석 기록의 과거 모델 사용 내역을 덮어쓰지 않는다.
