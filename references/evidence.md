# 근거와 판정 규칙

주장의 강도는 근거의 강도를 넘지 않아야 한다. 정적 분석으로 입증한 결함, 실제 배포 조건, 실행 중 도달 여부, 최종 영향을 각각 분리한다. 런타임 증거가 없다는 이유만으로 소스에서 입증된 결함을 무조건 추정으로 낮추지 않는다.

## 사실·가정·추론

모든 조사 노트와 보고서에서 다음 구분을 유지한다.

| 종류 | 의미 | 예시 |
| --- | --- | --- |
| 사실 | 인용한 자료가 직접 보여 주는 내용 | 지정한 함수가 전달받은 객체 ID로 조회하며 해당 함수 안에는 소유자 비교가 없음 |
| 가정 | 현재 자료로 확인하지 못한 필요 조건 | 외부 역할이 이 함수를 호출할 수 있음 |
| 추론 | 명시한 사실과 조건에서 도출한 판단 | 외부 호출 경로에 별도 인가가 없다면 다른 소유자의 객체가 반환될 수 있음 |

한 함수에 검사가 없다는 사실은 전체 경로에 검사가 없다는 사실과 다르다. “없음”이라는 주장은 검색·검토한 범위를 함께 명시한다. 설계 문서는 의도를 지지하지만 실행 코드의 동작을 대신 입증하지 않는다. 주석, 테스트, 예제, 기본 설정, 배포 정의도 각각의 적용 범위를 기록한다.

## 소스 참조

`source_refs[]`의 각 항목은 다음 필드를 사용한다.

| 필드 | 규칙 |
| --- | --- |
| `root_id` | 범위 목록에 등록한 소스 루트 식별자. 여러 저장소의 같은 경로를 구분한다. |
| `path` | 해당 루트 기준 상대 파일 경로. 경로만으로 주장을 대신하지 않는다. |
| `start_line`, `end_line` | 1부터 시작하는 포함 범위. 실제 읽은 스냅샷의 줄 번호를 사용한다. |
| `sha256` | 인용한 원본 파일 바이트 전체의 SHA-256. 정규화한 텍스트나 발췌문의 해시로 대체하지 않는다. |
| `symbol` | 관련 함수·클래스·설정 키·정책 구문 등 탐색 가능한 이름. 해당 없으면 스키마가 허용하는 빈 값으로 둔다. |
| `claim` | 이 참조가 직접 지지하는 좁은 주장. 경로 전체의 결론을 한 참조에 떠넘기지 않는다. |

루트 기록에는 가능하면 리비전과 작업 트리 변경 여부도 남긴다. 리비전만으로 미커밋 상태를 식별할 수 없으므로 파일 해시를 유지한다. 조사 중 파일이 바뀌면 이전 참조를 새 내용에 조용히 재사용하지 말고 재검토 여부를 표시한다. 접근 불가·미제공 자료에는 줄 번호나 해시를 만들어 넣지 않는다. 해당 항목은 불확실성과 다음 행동에 남긴다.

로그나 문서 등 보조 자료의 출처와 관찰 시점도 기록한다. 제공된 로그를 정적으로 읽을 수는 있지만, 새로운 실행을 유발해 근거를 얻지 않는다. 비밀값은 마스킹하고 위치와 종류만 남긴다.

## Finding 레코드

공통 필드는 다음과 같다. 실제 타입과 필수 여부는 키트에 포함된 스키마를 따른다.

| 필드 | 내용 |
| --- | --- |
| `id`, `title` | 안정적인 식별자와 구체적인 결함·조건을 담은 제목 |
| `status` | 아래 판정 상태 |
| `hypothesis` | 검토 중인 주장과 반증 가능한 조건 |
| `attacker`, `preconditions` | 초기 신원·통제 능력과 필요한 설정·권한·상태 |
| `invariant` | 깨지는 보안 성질과 그 근거 |
| `chain[]` | 간선별 흐름·권한 전환·조건·통제·근거·미확정 연결 |
| `source_refs[]` | 직접 확인한 소스 근거 |
| `counterevidence[]` | 가설을 막거나 좁히는 통제·분기·자료와 적용 범위 |
| `impact` | 입증된 효과와 추가 조건이 필요한 영향 확장을 구분한 서술 |
| `uncertainties[]` | 누락된 소스·설정·경로·외부 의존성, 판정에 미치는 영향 |
| `review` | 검토자 또는 검토 역할, 검토 범위·시점·판정 이유 |
| `next_action` | 남은 주장을 해소할 다음 정적 조사 행동 또는 종료 이유 |

기록을 채우기 위해 증거를 만들어 내지 않는다. 스키마에 맞는 빈 배열·빈 값이 허용되더라도, 판단에 중요한 공백은 `uncertainties[]`에서 설명한다.

모든 finding 후보의 `source_refs`는 하나 이상이어야 한다. 실제 코드 근거를 아직 확인하지 않은 도구 경고·힌트는 `notes/`에서 조사하고 근거 확보 후 후보로 등록한다. `observed` 연결은 참조 인덱스를 하나 이상 가져야 한다. 보고서에는 후보별 최소 코드 발췌, 루트·파일·줄·심볼·전체 해시, 각 연결과 통제·반증의 해석을 작성한다. 비밀값은 마스킹한다.

## 판정 상태

| 상태 | 사용 기준 |
| --- | --- |
| `hypothesis` | 조사할 만한 후보 주장이 있으나 아직 지지·기각 판단 전 |
| `source-supported` | 검토한 소스와 명시한 범위에서 결함을 지지할 충분한 근거가 있음. 실행 확인이나 모든 배포에서의 악용 가능성을 뜻하지 않음 |
| `conditional` | 명시한 미확정 조건이 충족될 때 경로나 영향이 성립함. 무엇이 사실이고 무엇이 조건인지 분리해야 함 |
| `needs-evidence` | 핵심 근거가 빠져 현재 주장 자체를 판단할 수 없음. 필요한 자료를 구체적으로 기록 |
| `rejected` | 반증 또는 잘못된 전제 때문에 현재 가설이 성립하지 않음. 기각 근거 보존 |
| `merged` | 동일 원인·경로의 다른 항목에 통합함. 통합 대상 ID와 고유한 근거 보존 |

전체 레코드의 상태 하나가 모든 부분 주장을 같은 강도로 만들지 않는다. `source-supported` 항목에서도 배포 도달성이나 후속 영향은 조건부일 수 있다. `conditional`은 “아마 위험함”을 뜻하는 포괄 상태가 아니다. 필요 조건과 그 조건을 확인할 자료가 있어야 한다. 단순한 미조사는 `needs-evidence`로 드러낸다.

심각도는 근거 상태와 별개다. 평가한다면 사용한 척도, 공격자의 초기 권한, 영향받는 자산, 필요한 조건과 근거를 적는다. 잠재 영향의 크기로 근거 부족을 덮지 않는다.

## 검토 범위 기록

파일·구성 요소·경로·불변조건 등 조사 단위와 그 경계를 먼저 정한다. 아래 두 기록을 분리해 유지한다.

1. **접근 이력:** 목록화한 범위, 실제 읽은 범위, 의미·경로 검토를 수행한 범위. 파일 수나 줄 수는 참고 정보이며 보안 검토의 대리 지표가 아니다.
2. **검토 상태:** 단위별 아래 상태, 이유, 관련 근거·노트, 남은 작업. 단위 내부의 일부 경로만 검토했다면 그 범위를 적는다.

| 상태 | 의미 |
| --- | --- |
| `reviewed` | 명시한 조사 질문과 단위 범위의 정적 검토를 마침. 무결함 보증이 아님 |
| `partial` | 일부 경로나 조건만 검토함. 완료 범위와 미검토 범위를 구분 |
| `unreviewed` | 범위에는 포함하지만 의미·경로 검토를 아직 수행하지 않음 |
| `blocked` | 자료·권한·해석 가능한 형식 등 특정 장애로 검토가 막힘. 장애와 필요한 자료 기록 |
| `excluded` | 명시한 범위 결정으로 조사에서 제외함. 제외 이유와 관련 위험의 관찰 한계 기록 |

예를 들어 파일을 전부 읽었어도 호출자와 인가 경계를 추적하지 않았다면 해당 경로는 `reviewed`가 아니다. 시작 시 전체 소스 목록을 고정하고 완료에는 파일·줄 및 필수 보안 경로 100% 검토를 요구한다. `reviewed` 참조의 구간 합집합을 현재 파일 해시와 대조하며 제외 상태로 분모를 줄이지 않는다. 비소스 분류·불투명 자료·외부 링크·목록 변경의 처리와 기술 스택별 전체 유형 대조는 [완료 규칙](completion.md)을 따른다.

## 반증 검토와 보고

`state.json`은 [state.schema.json](../schemas/state.schema.json)의 계약을 따른다. `active`는 준비·조사 진행 중, `partial`은 예산 종료 등을 포함해 검토가 남음, `blocked`는 필요한 자료·능력 부족으로 진행이 막힘이다. `complete`는 전체 소스 100%와 필수 경로·적용 유형·작업·후보 판정·보고서의 완료 검사를 모두 충족한 상태다. 무결함이나 모든 미지의 취약점 발견을 뜻하지 않는다. 필수 `next_actions`·`blockers`가 남으면 완료할 수 없으며 checkpoint와 일치시킨다.

가능한 결함은 진입점부터 순방향으로, 민감한 동작부터 역방향으로 검토한다. 중앙 인가, 래퍼, 저장 계층 정책, 입력 정규화, 실패 분기, 실행 사용자·마운트·IAM 조건이 주장을 바꾸는지 확인한다. 다른 검토자의 독립 검토가 없다면 있다고 표시하지 않는다. 검토자의 역할, 실행 클라이언트, 요청한 모델과 실제 확인한 모델·옵션을 구분해 기록하며 실제 값이 노출되지 않으면 미확인으로 남긴다.

각 결론에는 지지 근거, 반증 근거, 남은 조건, 검토 범위를 함께 제시한다. 산출물 검증기가 형식과 참조를 통과시켰다는 사실을 보안 결론의 정확성 검증으로 표현하지 않는다. 최종 보고서는 [보고서 템플릿](../templates/REPORT.md)을 사용하되, 해당 없는 항목에는 이유를 적고 발견하지 못한 내용을 안전성 주장으로 바꾸지 않는다.
